## 2. The offer / mechanic (what you're actually selling)

B2B buyers don't want a coupon — they want **reliability, predictable pricing,
and one phone number that always answers.** Lead with that.

**The Umuve PBC Partner Offer:**
- **Priority scheduling** — partner jobs jump the queue; same-day / next-day on turnovers.
- **Volume pricing** — a standing per-haul rate (e.g., flat trip + per-cubic-yard)
  instead of one-off retail pricing. Negotiate a simple rate card per partner.
- **One point of contact** — text/call a single number, no app friction required;
  you book it for them.
- **Partner code** — a unique code (e.g., `SUNRISEPM`) that (a) applies their
  agreed discount automatically and (b) lets Umuve attribute every booking to that
  partner so volume is measured and the relationship is provable.
- **Net terms once trust is built** — start prepaid/card-on-file, move to monthly
  invoicing for portfolios (the B2B portal supports org-level recurring + invoicing).

**Why the partner code matters operationally:** it's the smallest viable
attribution. Every `Job` that uses the code is stamped with `promo_code_id`, and
the code's `use_count` is your live tally of partner-driven jobs. No new tooling —
it's the existing promo system (see §5).

## 5. How a partner is onboarded in Umuve today

There are two working paths. For landing the **first** partner fast, use the
**Partner Code (promo) path** — it's the smallest viable, fully-wired mechanic.
Graduate high-volume portfolios to the **B2B Portal (Org) path** once proven.

### Path A — Partner Code (fastest, use this Monday)

A partner code is a `PromoCode`. It applies the agreed discount at booking AND
attributes every job to the partner via `Job.promo_code_id` (the code's
`use_count` is your live volume tally).

**Create the partner's code** (admin auth required):

```
POST /api/admin/promos
Authorization: Bearer <admin token>
Content-Type: application/json

{
  "code": "SUNRISEPM",          # partner's unique code (UPPERCASED server-side)
  "discount_type": "percentage", # or "fixed"
  "discount_value": 15,          # 15% off, or $ amount if fixed
  "min_order_amount": 0,
  "max_uses": null,              # null = unlimited (standing partner)
  "is_active": true
}
```

**Validate it works** (what the booking UI calls):

```
POST /api/promos/validate
{ "code": "SUNRISEPM", "order_amount": 250 }
```

**Then:** give the partner the code. Every booking they place (or you place for
them) with that code is discounted and attributed. To see partner volume:
`GET /api/admin/promos` → find the code → `use_count`.

**For recurring pickups** (HOA monthly, weekly turnovers), set up a
`RecurringBooking` for the partner's customer account:

```
POST /api/recurring
Authorization: Bearer <customer token>
{
  "frequency": "weekly",        # weekly | biweekly | monthly
  "day_of_week": 0,             # 0=Mon..6=Sun (weekly/biweekly)
  "preferred_time": "09:00",
  "address": "123 Sunrise Blvd, West Palm Beach FL"
}
```

The scheduler now **materializes each due recurring booking into a real Job AND
dispatches it to haulers automatically** (see "What changed" below). Before this
fix, recurring jobs were created but never sent to a driver — they sat in
`pending` forever. That gap is closed.

### Path B — B2B Portal / Org (for portfolios, once proven)

For multi-property managers who want org-level billing and net terms, use the
commercial portal (`portal.goumuve.com`, `/portal/v1/*`). It supports an `Org`
with units, `PortalRecurringSchedule` (org-level recurring), SSO, and monthly
invoicing. Jobs booked through it are stamped with `org_id`. This is the path
for a 200-unit management company on net-30 — not needed to land the first deal.

## What changed in the backend (so recurring actually fulfills)

Before: both recurring paths created `Job` rows but **never dispatched them** — a
materialized recurring job had no contractor notified and sat in `pending`.

Now: after materializing due recurring bookings, the scheduler and the
`/api/recurring/generate-next` admin endpoint call `auto_assign_job_async`, which
respects `DISPATCH_MODE` (assign-best-hauler or broadcast-to-all). A recurring
B2B pickup now flows end-to-end: due → Job created → hauler dispatched.

Files: `backend/scheduler.py`, `backend/routes/recurring.py`.
Requires `ENABLE_SCHEDULER=true` on the backend (already set in `render.yaml`).
